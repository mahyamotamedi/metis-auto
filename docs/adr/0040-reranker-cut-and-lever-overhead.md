# ADR-0040: The reranker cut is a token-sizing curve after S-6's dedup, chosen on tune by score mass, and overhead is an offline per-request estimate of apply

- Status: **proposed** by Saba (Pipeline A), 2026-11-02, for team review. Points 1 to 6 are as implemented in #23 and on branch `reranker-overhead-baselines`. The headline rule (point 3) is **provisional** (a proxy, not quality). Point 7 (T-2 to stretch) waits for the team's OK.
- Date: 2026-11-02
- Relates to: [ADR-0031](0031-full-data-lever-replay.md) (full-data lever replay), [ADR-0032](0032-lever-result-and-manifest-format.md) (lever results), [ADR-0036](0036-replay-scope-split-and-baselines.md) (split, baselines, units), [ADR-0038](0038-context-token-saving-conversion.md) (context saving conversion), [ADR-0022](0022-experiment-runner-and-run-tracking.md) (file-based run records); H-2, X5, FR-CTX-02, FR-CTX-03, FR-EVAL-02, QA-PERF, Q-14; sprint plan R-A2, L-1, T-2.
- Code: `experiments/context/exp-ctx-003-reranker-cut/version.py`, `experiments/context/exp-ctx-003-reranker-cut/config.toml`, `scripts/run_reranker_cut.py`, `scripts/measure_lever_overhead.py`.

## Context
R-A2 asks how many input tokens a cut of retrieved chunks to the best few would remove. The logs give each chunk's characters and the platform's `relevancy`, but nothing shows which chunks an answer used, and no quality ablation is approved (FR-CTX-03). About 36% of eligible chunk rows repeat inside a request, and S-6 (Pipeline C) already removes those copies, so the two savings must not be counted twice. The plan asks for a `LeverResult` per baseline (four baselines always), a per-version overhead against the 100 ms p95 target (L-1, Q-14), and a real `bge-reranker-v2-m3` run as cut-first item (a), on a local GPU only until the licence answer (O-1).

## Decision
1. **S-6 first, cut second.** Inside a request, chunk rows are collapsed with S-6's rule (same `h_exact`; `chunk_id` ignored; no fingerprint, no copy). Tokens removed by dedup are reported apart (`dedup_tokens_s6_not_counted`) and never counted in this saving. The cut's saving is (dedup + cut) minus (dedup alone), both taken from uncached input (ADR-0038).
2. **Cut rule.** On unique chunks ranked by score (ties by first position): keep the best `top_k`, drop those under `threshold`, but keep at least `floor` = 3. A unique chunk's score is the maximum of its copies' scores. A chunk without a score is always kept and counted (`rc_n_unscored`), never scored 0. Scorers: the platform's `relevancy` (*observed platform score*, evidence class *hypothetical reconstruction*) and `lexical_overlap` (*heuristic*, on a seeded 2,000-request sample; text in memory only). The scorer is injected, so tests need no model.
3. **Headline chosen on tune, read once on report.** Thresholds are the 10/25/50% quantiles of tune-period unique-chunk scores. The headline is the tune point that removes the most tokens while keeping at least 90% of the score mass (sum of unique-chunk scores); ties go to the larger `top_k`, then the lower threshold; if no point qualifies, the gentlest point, labelled so. The report period never sets a threshold. Every setting is in `config.toml` and the config hash.
4. **One result per scorer and baseline.** The four baselines follow ADR-0036 and ADR-0038 unchanged: `as_logged` at implied input rates (recorded units), the three repriced baselines through `baselines_full.repriced_row_costs` (price-file units, no `fees` key). Files are `reports/levers/context.reranker_cut.<scorer>.<baseline>.json`. The `lever_id` stays `context.reranker_cut.<scorer>`, **without** the baseline, because L-1 finds every baseline's file of one version by `lever_id`.
5. **Pricing is accounting, outside `apply`.** `apply` adds only counts, characters, tokens and scores; `RerankerCut.baseline_frames` prices the cut per baseline, as S-6b does. `apply` changes no recorded cost.
6. **Overhead (L-1).** `scripts/measure_lever_overhead.py` times `apply` with `perf_counter_ns` on 1,000 seeded report-period LLM rows, one row per call, after one warm-up call, with data (chunks, text) loaded before timing. It writes p50 and p95 into every result of that `lever_id`, adds the label "offline per-request estimate on a local machine; not a load test (Q-14)", and leaves the manifest and savings unchanged. A version that raises writes nothing.
7. **Not done, by decision.** Cut-first (a), the real `bge-reranker-v2-m3` run, is not run: there is no approved local GPU run and no licence answer, so R-A2 stays a token-sizing curve, as the plan's "GPU unavailable" fallback allows. T-2 (MLflow tracking) moves to stretch, per the plan's Risks row; run records stay file-based (ADR-0022). Pending the team's OK.

## Alternatives considered
- **Cut before dedup, or count dedup in this saving:** double-counts S-6's saving. Rejected.
- **Score a missing relevancy as 0:** would drop chunks for lack of data. Rejected (unknown is not zero).
- **Choose thresholds or the headline on the report period:** reads the report period more than once and fits to it. Rejected.
- **A fixed `top_k` without a quality proxy:** no rule for where to stop. The score-mass rule is a proxy chosen before results; a quality ablation would replace it.
- **Put the baseline in `lever_id`, as S-6b does:** each baseline file would look like a separate version to L-1 and to the comparison. Rejected; the file name carries the baseline.
- **Price inside `apply`:** `repriced_row_costs` needs a premium and a cheap model that a version does not hold, and the overhead would time accounting work that serving never does. Rejected. Consequence: p95 fell from 86.4 / 96.5 ms to 28.2 / 35.3 ms.
- **Time `apply` on one large batch:** hides per-request cost and tail latency. Rejected; per-row calls are reported, with batching possible as an option.
- **A load test:** out of scope for an offline replay (stretch).

## Consequences
- Every R-A2 number is "tokens only, quality not measured"; a cut can remove the chunk an answer needed.
- The headline can change if the score-mass threshold changes; it is a proxy, not a quality gate.
- `todays_models` covers only about 9% of eligible requests while `gemini-2.5-flash` has no price in the sprint catalogue; the other three baselines cover all of them.
- `lever_id` naming differs from S-6b's; a shared convention is a team decision.
- Overhead numbers are one machine's offline estimate (AMD Ryzen 7 5800H, CPython 3.13.9); they exclude data loading and pricing.
- Without the real reranker, scores are the platform's or a heuristic; cut-first (a) can replace the scorer through the same injected interface.
