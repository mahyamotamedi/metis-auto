## Context

The final plan's paid branch asks for P-1 (300 report-period requests through E4, quotas by bot rank, language, RAG, length and turn, no tenant above 35%, a 20-request pilot first), P-2 (two judges from different families, both answer orders, strict JSON, a 60-item human spot-check) and P-3 (labels to R-B3 and R-C3). E4 (sampling run) and E5 (pairwise judging) exist but run only with fakes: nothing built live clients for the harness, and no real judge existed. The four machines keep separate ledgers that nothing sums (decision 7).

Facts that shape the design (all checked 2026-11-03):
- **Arms:** `gpt-4.1-nano` is retired (Metis passes through OpenAI's HTTP 404 "has been deprecated"); `mimo-v2.5` answers HTTP 400 "Unsupported model" in every request shape (TODO-17, Q-42). `gpt-4o-mini` works. Jev is a decision model, not a chat model (ADR-0047).
- **Strict JSON:** Metis's OpenAI wrapper rejected `response_format` `json_schema` (HTTP 400 on gpt-4o-mini, router live check); JSON mode is not verified there.
- **Budget:** the 20 USD ceiling and lifetime cap (ADR-0018 amendment 2) were approved for the golden answers, which spent **12.03 USD** (`reports/evaluation/golden_v2/answers_ga-v2-20261101_summary.json`). At most about 7.97 USD is left for the whole team, so the plan's 300-request run (estimated 20–25 USD) cannot fit.
- **golden-v2** (ADR-0029): 300 text-only records with gpt-5.5 reference answers already paid for (ADR-0030).

## Decision

1. **The pilot set is golden-v2, not a new report-period sample** (provisional, owner to confirm). The reference answers exist, so judging needs no new reference call, and the set's selection, caveats and fingerprint are already reviewed.
   - **Trade-offs (stated, not hidden):**
     - its quotas are golden-v1's (cohort, intent, language, position, length, bot class), not the plan's (bot rank, language, RAG, length, turn);
     - it **has no attachment requests** (ADR-0029);
     - only **44 of 300** records fall in the plan's report period (Aug–Oct 2026), so it is not a report-period sample, and labels from it are training data for R-B3 / R-C3, not a held-out report.
   - **Tenant cap:** checked on the committed ID-only export: the largest single account holds **20%**; the pooled "Remaining accounts" cohort (127 accounts) holds 25%, an upper bound for any one of its accounts: **passes 35%**. The 20-record pilot (seeded, round-robin over languages, capped at ⌊0.35 × 20⌋ = 7 per tenant) has at most 30%.
2. **Arms are checked, never assumed.** An arm is callable only if it is in the catalogue, enabled, priced, served by an enabled OpenAI-compatible endpoint, and not on `[arms.not_callable]`, which holds the live-check facts (gpt-4.1-nano, mimo-v2.5, jev-latest) with their evidence. Any other arm is refused with its reason in the plan; a run plans calls for callable arms only, so it never crashes on a gone model. The catalogue flags stay the catalogue owner's change (TODO-17); this list keeps the models out until it lands. Callable today: `gpt-5-nano`, `gpt-4o-mini`, `deepseek-v4-flash`. The reference `gpt-5.5` is never called again; the free logged-answer arm is not wired yet (TODO-21).
3. **Live clients for E4, built from settings, replay first.** Per run, `ReplayFirstClient(recorded answers, SpendGuardedClient(recording(live)))`:
   - `build_live_client` (ADR-0021) refuses unless both keys (`live.enabled`, `METIS_API_KEY`) and the caps are set;
   - every live answer is recorded (`data/recorded/`), and an input already recorded is **replayed** (same model, same exact input; ADR-0014), so a rerun costs nothing;
   - each live call passes the spend guard (pre-call estimate at the generation limit, then the actual cost) over the shared ledger of point 5; a refused call returns a `ModelError` (`spend_guard_refused`) that E4 records, and the run goes on;
   - E4's own guards still apply: the owner's `LiveApproval` (who, run, cap, dataset text approved), the per-call worst case against the run cap, and `uses_sample_conversations = True`.
   - Each arm gets **the prompt the gpt-5.5 reference got** (golden answers' `build_request` with the reference run's layout, `dataset_positions`).
4. **The judge is strict JSON by prompt and parser.** `LlmPairwiseJudge` implements E5's `PairwiseJudge` unchanged and asks for exactly `{"choice": "first" | "second" | "tie"}`. It sends no `response_format` (point of fact above); the parser refuses anything else (prose, extra keys, two objects, wrong case) with a reason, and only unwraps one fenced block deterministically. Both answer orders (E5), two judges whose catalogue families differ (`require_two_families`), and each call's cost and latency recorded as **evaluation cost**. A refused output or a failed call becomes `not_evaluated` with its reason, never a crash and never a guess. Judge models, their limit and the instruction language (`en`/`fa`) are owner decisions (Q-63).
5. **One shared spend total (decision 7).** Each machine exports a content-free summary of its own ledger (`scripts/spend_share.py export`: totals per run, no prompt, no key; read-only) into `reports/spend/ledgers/<machine>.json`. A paid run uses `SharedSpendLedger`: what is left is the smaller of the local ledger's own remainder and `ceiling − (other machines' newest totals + this machine's total)`. It **fails closed**: a missing machine, a summary older than `max_age_hours`, or this machine's own summary among the others refuses. Charges still go only to the local ledger; no ledger is ever edited or deleted. The machine list and maximum age are owner / team values (Q-64).
6. **P-3 labels are derived, not guessed.** An arm is acceptable for a record when **both** judges' pairwise scores against gpt-5.5 reach `acceptable_score` (owner, Q-63); disagreement or a missing judgment leaves it unknown. `cheap_ok` (some `cheap_arms` arm acceptable; owner) is R-C3's boolean label, and `min_adequate_tier` is the routing plan's L2 label. The source is `benchmark:<name>`, which R-C3 accepts unchanged (tested against its `fit_logistic`). The label file (with the join key `user_message_id`) stays in git-ignored `runs/`; only its counts may be committed. R-B3 refuses every label source today (TODO-22).
7. **The plan makes no call.** `scripts/benchmark.py plan` prints the arms (callable or why not), the record count, generation and judge calls, cost bounds against the caps and the shared total, the three gates and every unset owner value. With `--with-db` (the machine holding golden-v2 and the gpt-5.5 answers) it counts input sizes and prices them. `generate` and `judge` refuse, listing every reason, until gate 2 (Metis's written answer, `gates.metis_allows_samples` with its reference), the owner's per-run approval and the owner values are set.
8. **Human spot-check:** 60 judged pairs (seeded, round-robin over languages), an **ID-only, blinded** sheet (opaque `s01`… IDs; no model, no record), the text and the key in separate local files under `runs/`.

## Alternatives considered

- **A new 300-request report-period sample through E4 allocation**, as the plan wrote it: closer to the plan's quotas and period, but it needs new reference answers (about 12 USD for 300 at gpt-5.5's observed cost) on top of the arms and judges, which the remaining credit cannot carry. Kept as the main run's design if the owner funds it; the harness is the same.
- **`response_format` (`json_schema` or `json_object`) for the judge:** rejected or unverified on Metis's wrapper; a provider-side guarantee that fails would turn every judge call into an error.
- **Lenient parsing (search the reply for "first"):** guesses, and a guess is a label.
- **Summing the ledgers by hand in `sprint-notes.md`** (decision 7's text): nothing enforces it before a call; the summary files make the sum mechanical and the guard enforces it.
- **One machine holds all keys and runs every paid call:** simplest for spend, but it puts every machine's other live work behind one person; kept as an operating choice, compatible with point 5.

## Consequences

- A pilot can start on the database machine once the owner sets the values and the gates open; until then every paid step refuses with all its reasons.
- **Budget:** at most about 7.97 USD remains under the 20 USD ceiling (golden answers 12.03 USD, Parham's router checks 0.0049 USD; other machines unknown until their summaries exist). The 300-request main run does not fit; the pilot's printed bound decides whether it does. **Update 2026-11-03:** [ADR-0018 amendment 3](0018-live-calls-for-development-under-a-lifetime-budget.md) raised the ceiling and lifetime cap to 92 USD (80 USD credit left plus the 12.03 USD already spent, an upper bound), so the 7.97 USD bound above no longer applies.
- Labels from golden-v2 are training labels for R-B3 / R-C3; any "quality" claim stays conditional on the judges' Persian validation (the E5 gate, owner) and the 60-item spot-check.
- Not changed: E4, E5, the golden-answers code, the ledger, R-B3 and R-C3 (used, not edited); the catalogue and `sprint.toml` (their owners' changes, TODO-17).

## Amendment 1 (2026-11-03): swap-inconsistent pairs, the Persian gate on labels, spot-check agreement

Status: **provisional**; review by Parham (owner of these files) pending. Reason: a review of the code above found that a judge whose two orders disagreed was still scored (the E5 mean made it look like a tie), that labels said nothing about whether the judges were validated for Persian, and that nothing turned the filled spot-check sheet into numbers. Public names and shapes of `evaluation/sampling` and `evaluation/judging` (E4, E5) are unchanged; everything below is added.

**Changed**
1. **A swap-inconsistent pair is not a tie and not a score.** E5 already defines it (`PairOutcome.swap_consistent`, true when both orders map to the same verdict); `judge_all` now turns an inconsistent judged outcome into state `inconsistent` (reason `swap_inconsistent`, no score, no preference) with `dataclasses.replace`, so E5's types and diagnostics are untouched. The paid calls stay in the cost totals. A genuine tie (both orders `tie`) is still 0.5. In the labels, an arm with an inconsistent pair for either judge is NA (never guessed from the other judge's score) and a record with nothing else labelled is `not_labelled:inconsistent`; the summary reports the inconsistency rate per judge and per arm.
2. **`judge_gate` per label row and in the summary.** `validated` / `unvalidated` / `not_configured` by language group, from E5's `evaluate_gate` on the spot-check agreement when the `[gate]` values (E5 `GateConfig`: statistic, minimum agreement, minimum items) are set, else `not_configured`; a language is validated only when both judges pass. Label values are unchanged and no row is dropped. R-C3 may report on labels that are not validated but must not move on them (`benchmark_labels.md`). The file format stays `benchmark-labels-v1` (additive columns `inconsistent_arms`, `judge_gate`).
3. **`scripts/benchmark.py agreement --run-id <run>`** reads the filled `spot_check/sheet.csv` and `key_LOCAL_ONLY.csv`, maps them to E5's rating import (`read_ratings`, strict-majority consensus), computes agreement per judge and language with E5's `agreement`, evaluates the gate, and writes the content-free `runs/benchmark/<run>/agreement.json` (counts and statistics only). Missing ratings give `insufficient`; unset gate values give `not_configured`. It makes no call. Agreement has no confidence interval yet (no bootstrap is passed), so E5's gate compares the point value.

**Known limits (review findings not changed here; each is a follow-up, finding 4 only on the owner's say-so)**
- Arms and the reference are generated with the reasoning effort and output-token limits of their own settings; a difference in either is confounded with the model in the labels.
- The two judges' families may overlap with the answering arms' families (self-preference); `require_two_families` only compares the judges with each other.
- A reasoning judge can spend its output limit on reasoning and return empty text; that becomes `not_evaluated`, not a retry.
- Strata can be empty in the pilot's quotas, and E5's bootstrap clusters by record (`session_ref` is the record ID), not by session.
- Replayed answers are counted as spend in the plan's bound although they cost nothing.
- `LabelRow.judges` is always 2 (the constructor demands two judges).
- `SharedSpendLedger` raises a `TypeError` on a timezone-naive summary timestamp instead of refusing with a reason.
- A missing catalogue tier for an arm raises a `KeyError` in the labels instead of a refusal.
- The gate values are owner decisions (not listed by `unset_owner_values`); until set, labels are `not_configured` and Persian quality claims stay conditional.

## Amendment 2 (2026-11-03): a transient provider error no longer stops a paid run

Status: **provisional**. Reason: the pilot's generation and judging each stopped after a single Metis connection timeout (about 50 s): the spend guard cannot price a call with no reported usage, so it charged the pre-call estimate and stopped **every** later call in the run (ADR-0021), including a whole second judge that never got a call.

**Changed (benchmark only).** `SpendGuardedClient` (`wiring/benchmark.py`) treats a `connection` or `timeout` error as transient: it charges the pre-call estimate (conservative, never zero, bounded by the cap, since the provider may still have billed the request) and lets the run go on. After `max_consecutive_transient` (5) such errors in a row it stops the run (an outage), and any success resets the streak. Every other uncomputable cost (missing price, unmapped model, an unknown error) still stops the run as before. `SpendGuard` itself, the pipeline and the router cascade are unchanged. Tests: `tests/unit/wiring/test_benchmark_transient_errors.py`.

**Consequence.** A flaky connection costs one estimate per failed call instead of the run. A failed call is still recorded as an error and is retried by the next pass (resume with the same run ID; recorded answers replay free).

## Amendment 3 (2026-11-03): the pilot goes through the evaluation framework

Status: **provisional**. Reason: the pilot ran E4's harness for generation and E5's pairwise judging, but nothing connected its results to the framework's comparison (E1/E4/E6): the generation `RunResult` was not saved (the CLI printed only its type), and no script called `comparison_table` or the report builder on a real run.

**Added.** `evaluation/benchmark/framework_report.py` rebuilds the answering run from the recordings (each recorded live answer through E4's own record builder, now public as `call_record`; judge calls and records not made live are skipped; per case and arm a complete answer wins over a partial one over an error) and gives it to E4's `comparison_table`: one row per language (Persian first) and model with n, error share, cost, latency and quality as separate columns and no combined score. Quality is one table **per judge, never merged**, `estimated`, and marked not validated unless that language's Persian gate (amendment 1) says `validated`. `scripts/benchmark.py framework-report --run-id <run>` writes `framework_report.json` and `.md` under `runs/benchmark/<run>/` (content-free: model names, counts, statistics). E4's and E5's names and shapes are unchanged (one function added to `sampling/runner.py`).

**Limits.** The run is reconstructed: its caps, retries and stop rules are not the original's, and the report says so. The minimum n and the bootstrap are owner decisions and stay unset, so every row is `descriptive` and no interval is shown. The full E6 `build_comparison_report` (effects against the reference, non-inferiority, scenarios) is not run: it needs delta, a minimum n, bootstrap settings, a price age and scenarios, all unset.

## Amendment 4 (2026-11-03): the framework applies its own rules to the pipelines' lever results

Status: **provisional**. Reason: the framework (E0 to E6, `evaluation/`) and the pipelines (cache, context, routing; `LeverResult` in `analysis/`) were never connected. A `LeverResult` has no quality measure, so the final plan's decision rules, which all depend on quality, were applied by hand in `sprint_decisions.md`. The layer rules forbid `evaluation` from importing `analysis`.

**Added.** `evaluation/reporting/lever_verdicts.py` (pure, plain mappings in), `wiring/lever_evaluation.py` and `scripts/evaluate_levers.py`. For each result the framework gives: the saving share with its interval and provenance (the evidence class mapped to measured, estimated or simulated), its units (recorded, repriced, estimate only), the Persian slice as its own line, the quality side (`not_measured`, `sampled` with n, or `measured`) and the plan's decision rule for its step. A saving without an interval makes no claim.

**A rule is judged only on what the file holds.** Context without the paid ablation and routing without judge-corrected labels are `cannot_pass` (tokens only, cost only). An answer cache needs about 300 reviewed hits (a parameter) and then an error count the file does not hold; a retrieval cache needs an agreement of 0.9 the file does not hold: both are `not_evaluated` with the reason. A cache version of an unknown kind is not guessed. Nothing passes by default and `pickable` is empty unless a rule is passed on the file's own evidence. Results are grouped by baseline, requests, price version and evidence class and never ranked across groups.

**Not done.** Replaying levers per request through E3 and E4 (needs request-level logs and quality scores that do not exist), ranking inside a group, adding quality fields to `LeverResult` (the pipelines' contract), and any use of the benchmark's judge scores. The result on the 132 files of 2026-11-03 is in the progress entry `2026-11-03-framework-evaluates-lever-results.md`.

## Amendment 5 (2026-11-04): callable models only, DeepSeek V4.1 as the DeepSeek judge, self-preference reported apart

Status: **provisional**; owner decision on the judge change: the project owner, 2026-11-04. Reason: the main run needs a list of models Metis serves today, the DeepSeek judge was to move to V4.1, and the review limit of amendment 1 ("the two judges' families may overlap with the answering arms' families") had no handling.

**Model list (evidence: [metis_model_availability_2026-11-04.md](../references/metis_model_availability_2026-11-04.md)).** The wrapper documents no model-list endpoint, so one tiny SYNTHETIC call per model was made (0.003271 USD in the shared ledger, including two failed calls charged at their pre-call estimates). `gpt-5-nano`, `gpt-4o-mini`, `deepseek-v4-flash` and `deepseek-v4.1-flash` answer; `gpt-4.1-nano` is HTTP 404 and `mimo-v2.5` HTTP 400 again. `[arms] requested` now lists callable models only (`gpt-5-nano`, `gpt-4o-mini`, `deepseek-v4-flash`); the two retired models stay under `[arms.not_callable]` with the new date.

**DeepSeek V4.1.** `deepseek-v4.1-flash` is accepted under its own ID. The wrapper reports the model name `deepseek-flash` for it and for `deepseek-v4-flash`, with the same input count: as far as the wrapper shows they are one served model (V4.1-Flash-1017), an inference from the reported name, not a statement by Metis. The prices on the pricing page are the same.

**Changed.**
1. **Judges:** `judges.models = ["gpt-4o-mini", "deepseek-v4.1-flash"]`. The DeepSeek judge needs `thinking = "disabled"` under `[model_options."deepseek-v4.1-flash"]` in `config/local.toml` (documented in `config/local.example.toml`); with thinking on, hidden reasoning (about 30 tokens) uses up the 64-token reply limit. A reply that is nevertheless empty is `not_evaluated` (`judge_output_invalid:empty_output`), never a guess. Whether a 64-token V4.1 reply is non-empty with thinking disabled is checked by `scripts/judge_reply_check.py` (one SYNTHETIC pair); result 2026-11-04: a valid reply (6 output tokens, thinking disabled); see the progress entry.
2. **Reference files:** the live defaults and the hash-locked catalogue and price files stay unchanged (ADR-0026). New copies `catalogue-metis-test-2026-11-04-v41.toml` (gpt-4.1-nano and mimo-v2.5 disabled with their evidence; `deepseek-v4.1-flash` added, enabled, window and output limit from DeepSeek's pricing page for V4.1-Flash-1017, wrapper-side limits unverified, A-57) and `prices-metis-2026-11-04-v41.toml` (one row added, from the saved pricing page). The benchmark loads them through the new `benchmark.toml [reference]`. `catalogue-metis-replay.toml` and `sprint.toml` (baselines) are not changed: a replay catalogue is a pricing aid, and `sprint.toml [routing]` already excludes both models.
3. **Judge versions are never mixed.** Each judge model writes its own files (`judging/<model>.*`). The pilot's scores from the earlier DeepSeek judge (`deepseek-v4-flash`) stay as they are, as a separate judge version; labels and the headline read only the configured judges.
4. **Self-preference.** Both judges are also answering families (OpenAI: `gpt-4o-mini` judges `gpt-4o-mini` and `gpt-5-nano`; DeepSeek: V4.1 judges `deepseek-v4-flash`, the same served model). `framework_report` now adds `self_preference` (`split_by_family`): every (judge, language, arm) row whose judge family equals the arm's family goes to `same_family`, the others to `headline`. **The headline of an arm is its score without its own family's judge**; same-family rows are reported apart and never averaged in. The per-judge tables are unchanged and still never merged.
5. `framework-report --scope main` rebuilds the main set (300 records) from every live recording in the recorded folder, because the pilot's 20 answers replay under an earlier run ID.

**Not changed, stated.** The labels (point 6: an arm is acceptable only when both judges reach `acceptable_score`) still use both judges, including the same-family one; `cheap_ok` for an arm whose family judges it is therefore not independent of that judge. A label rule that uses only the cross-family judge, or a third family, is an owner decision (open question, not yet numbered); until then the 60-item spot-check is the control and the labels say so in the report. The self-preference split covers framework reports, not the label file.

**Consequences.** The pilot's old DeepSeek-judge scores cannot be compared with V4.1 scores. The kNN router results of 2026-11-03 (candidates `gpt-4.1-nano`, `mimo-v2.5`) are stale and listed in the availability note; they are not re-run here.

**Addition to amendment 5 (2026-11-04, main run): an intermittent `model_not_found` is transient.** During generation of `p1-main-1` the wrapper answered HTTP 404 `model_not_found` for `deepseek-v4-flash` twice in about 60 calls, on different records, while the same model answered the calls around them, and the run stopped each time (the guard stops on any uncomputable cost other than connection or timeout). `SpendGuardedClient` now treats `http_404:model_not_found` like a connection error: it charges the pre-call estimate and goes on, and the streak limit (5 in a row) stops the run when a model is really gone. Test: `tests/unit/wiring/test_benchmark_transient_errors.py`. The failed answers are retried by resuming the same run ID.
