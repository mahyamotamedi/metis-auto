# ADR-0059: Redis and MLflow live in a `services` extra with its own lock, each behind one adapter module; Compose starts them in a `services` profile on loopback only

- Status: **provisional** (sprint tasks T-0, T-2 and T-4, 2026-11-04). The `pyproject.toml` change was approved by the owner on 2026-11-04. Nothing here was started against a real server or image while it was written.
- Date: 2026-11-04
- Relates to: [ADR-0001](0001-python-tooling.md) (locks, two-week age rule), [ADR-0009](0009-repository-structure-and-dependency-rules.md) (layers), [ADR-0022](0022-experiment-runner-and-run-tracking.md) and [ADR-0032](0032-lever-result-and-manifest-format.md) point 8 (MLflow only as an exporter, never the record), [ADR-0027](0027-local-postgresql-foundation.md), [ADR-0033](0033-postgres-event-sink-layout.md), [ADR-0035](0035-ci-github-actions.md) and Amendment 1 (CI pins), [ADR-0049](0049-redis-cache-store-and-store-switch.md); QA-REPL, QA-REPRO, QA-PRIV, QA-TEST.
- Code: `pyproject.toml` (`services` extra, `services` marker), `requirements-services.lock`, `constraints-services-min-age.txt`, `src/metis_auto/ports/tracking.py`, `src/metis_auto/adapters/tracking/mlflow_tracker.py`, `scripts/log_levers.py`, `compose.yaml`, `Dockerfile` (`demo` target), `.github/workflows/ci.yml`.

## Context
The sprint plan asks for Redis, Postgres and MLflow added "without touching the pipeline" and started with one command. Redis (T-1, ADR-0049) and the Postgres sink (T-3, ADR-0033) exist as adapters; MLflow tracking and the Compose services do not. ADR-0022 chose a small own runner and allowed MLflow only as a read-only exporter of the content-free `LeverResult` JSON, which stays the record. psycopg is already in the `db` extra.

## Decision
1. **One new extra, `services`**: `redis` and `mlflow-skinny` only. psycopg stays in `db`. It has its own lock, `requirements-services.lock` (the dev lock plus the extra, shared pins equal, versions chosen under `constraints-min-age.txt` and `constraints-services-min-age.txt`, cutoff 2026-10-20; compiled with `--only-binary :all:` and hashes from PyPI's published digests), never in the runtime or dev lock. A `services` pytest marker is added; real-server tests skip themselves when no server answers and can be selected with `-m services`. The default test run needs no server and no service library.
2. **Each library is imported in exactly one module**: `redis` in `adapters/stores/redis_store.py` (lazily), `mlflow` in `adapters/tracking/mlflow_tracker.py`. The Postgres event sink imports no database driver (the connection is injected); psycopg stays confined to `data_access/postgres` by the existing db rule.
3. **A `RunTracker` port** (`ports/tracking.py`): `log_result(result: Mapping[str, object]) -> str` returns the run ID. A plain mapping, because `ports` may not import `analysis`. The MLflow adapter logs one run per lever result: the manifest as parameters, the savings, the baseline cost and the interval as metrics, `correctness_state`, evidence class and slice names as tags, and the result JSON as an artifact (ADR-0032 point 8: slices and correctness are kept, not flattened away). **Idempotent** by `lever_id` + `config_hash`: logging the same result again returns the existing run. Only the manifest's reproducibility pins (`data_revision`, `code_commit`, `config_hash`) are hashes that may reach MLflow; no text, ID or other hash does (tested over everything logged). The JSON files stay the record.
4. **Compose**: `redis`, `mlflow` and `demo` are added and, with `postgres`, put in a `services` profile; `postgres` keeps its `db` profile. Ports are bound to `127.0.0.1`, every service has a health check, passwords come only from the environment (`METIS_DB_PASSWORD`, `METIS_REDIS_PASSWORD`), and the demo uses Redis and Postgres through `METIS__*` configuration overrides only. A Dockerfile `demo` target installs the ui, services and db locks. CI validates the file with `docker compose --profile db --profile services config -q` on the Linux job (no image is pulled, nothing starts); the ADR-0035 Amendment 1 pins are unchanged.

## Alternatives considered
- **Full `mlflow` instead of `mlflow-skinny`:** brings the server and UI dependencies (flask, gunicorn, sqlalchemy) into the lock for a client-only job. Rejected for the lock; the UI runs from the container image in Compose. (`mlflow-skinny` cannot serve the UI itself.)
- **MLflow as the record:** rejected again (ADR-0022, ADR-0032 point 8): free-form parameters do not carry privacy classes.
- **Services in the dev lock or the db extra:** every contributor would install them. Rejected.

## Consequences
- The services are optional; without them nothing changes. A result logged twice makes one run.
- The `redis` and `mlflow` image tags in `compose.yaml` and the `demo` image build were not pulled or built when written; they are checked on the first `up` (Docker pulls need the owner's say). Tags, not digests, are used for those two images, as for `postgres`.
- MLflow's file store is in maintenance mode upstream (ADR-0022 noted it): MLflow 3.17 refuses it unless `MLFLOW_ALLOW_FILE_STORE=true`, which the adapter sets for `file:` URIs; `scripts/log_levers.py` writes `runs/mlruns` (git-ignored). `mlflow-skinny` cannot serve the UI; the Compose server uses SQLite and the container image.
- Guarding tests: `tests/architecture/test_service_imports.py` (`test_redis_imported_only_in_redis_store`, `test_mlflow_imported_only_in_mlflow_tracker`, `test_postgres_sink_imports_no_database_library`, planted-import tests), `tests/architecture/test_compose_services.py`, `tests/architecture/test_ci_workflow.py` (`test_the_compose_file_is_validated_without_pulling_or_starting_anything`), `tests/unit/adapters/test_mlflow_tracker.py` (idempotent by `lever_id` + `config_hash`, manifest as parameters, nothing but the manifest pins as hashes), `tests/integration/test_mlflow_filestore.py`.
