## Context
The sprint (Days 1 to 3) measured three things that can run live on a typed message: the decision router in its rules-only mode (ADR-0064), the within-message chunk dedup (exp-ctx-001, ADR-0038) and the exact cache. The demo already holds the decision router as a routing mode (ADR-0047, R7), the bot-level cache scope (ADR-0023 point 5) and a compression toggle. It lists the retired models `gpt-4.1-nano` and `mimo-v2.5` as candidates, offers the local, hosted and hybrid router backends in its toggles, and has no dedup. No result of the sprint is quality-checked: quality is measured for no step.

## Decision
### Routing (Part 1)
1. **Verified, not assumed:** `pipeline.routing.policy = "decision_router"` with `router.mode = "off"` runs end to end offline in the chat and demo pipeline: gate, rules, safe tier. `decision_router` on the pipeline is `None` (no cascade, no backend), the fake client is called once for the answer, and nothing is spent (`tests/integration/test_demo_sprint_winners.py`).
2. **Demo routing choices:** `decision_router` (rules only; labelled "sprint winner, provisional: cost only, pending quality"), `sticky_v1` (placeholder) with a new `inner` choice `rule_based | decision_router`, and `per_request` (rule-based, placeholder). The serving default stays `fixed_model`. The chat session's default `router_mode` is now `off`.
3. **Candidates:** a new `RoutingConfig.candidates` (empty = every enabled model, the serving default). Every non-fixed demo routing sets it from `config/evaluation/sprint.toml` `[routing] candidates` (`gpt-5-nano`, `gpt-4o-mini`, `deepseek-v4-flash`), read at run time so the demo routes over what the sprint measured. A model outside it is excluded with the new reason `not_a_candidate`. This keeps `gpt-4.1-nano` and `mimo-v2.5` out; both are `enabled = false` in `catalogue-metis-test-2026-11-04-v41.toml` (a test checks that the sprint set is enabled there and holds no retired model). The live default catalogue file is hash-locked and unchanged. (`deepseek-v4.1-flash` is enabled in the 2026-11-04 catalogue but is not in the sprint set, so the demo does not route to it.)
4. **Visibility:** the `TurnReport` routing block and the UI details carry the tier, the reason code and, when the safe tier took the request, a note that most traffic lands there (ADR-0064: about 96% of replayed requests, and its only primary candidate is `gpt-4o-mini`). The note says nothing about quality.
5. **Backends off:** the demo toggles offer only `DEMO_ROUTER_MODES = ("off",)`. The local, hosted and hybrid modes remain in `ROUTER_MODES` for diagnostics and tests and are unreachable from `scripts/chat.py` and the UI.

### Within-message dedup (Part 2)
6. **Semantics** (re-implemented in `domain`; `experiments/` is read only as a reference): inside one message's retrieved context an item is an exact duplicate when an earlier item has identical text; the first copy is kept, later ones are removed, order is stable. Identity is the text, not the document reference. An item with blank text is never a duplicate. Instructions, history and the current message are never touched. **No pointer or placeholder** is put in the prompt: the sprint version had none (it counted and dropped), so a removed copy is simply absent and no lossy rewrite exists.
7. **Selection:** the context strategy `within_message_dedup` (and `within_message_dedup_dataset_positions` for a real bot's layout), registered in `CONTEXT_STRATEGIES`. It wraps a layout strategy and exposes a `reduce` hook. `[pipeline.context.dedup] enabled` is the switch, **off by default**; with it off the strategy sends exactly what `pass_through` sends (tested byte for byte).
8. **Order with compression: dedup first, then compression.** The pipeline applies `reduce` before compression and before the target's tokens are counted, so counts, parts, cost and compression all describe the request actually sent. With both on, compression sees only the surviving items; the composition row of a component that had both reads `compressed` while `items_total` and `items_kept` still show the dedup, and the `context_deduped` event holds the exact sizes. The only change to compression code is that `compression.mark` also accepts a `deduplicated` row (a one-line tolerance); compression behaviour with dedup off is unchanged (tested).
9. **Contract (schema 0.8 → 0.9):** `ContextAction.DEDUPLICATED`, `ExclusionReason.NOT_A_CANDIDATE`, span `context.dedup` (overhead), event `context_deduped` (`strategy` operational; `items_total`, `items_removed`, `chars_removed` derived: sizes only, no text, no fingerprint). `contracts_reference.md` is regenerated; the contract tests are green.
10. **Accounting:** the removed tokens reach the decomposition **through the request actually sent**: the chosen model's cost on the full request less the cost on the sent request is the existing `compression_saving` term, which now reads as the **context term** (dedup plus compression; label "Context (dedup + compression)"). A separate decomposition term was rejected: it would change the fixed order and identity of brief §6 and every consumer of it. The dedup share is shown **separately** as a labelled sub-line (`AccountingService.dedup_effect`: full less deduped, same chosen model, same answer): chunks, tokens (with their fidelity), money, per message and per session. The fixed order and the exact sum still hold (tested). **Conversion:** ADR-0038 converts characters to tokens (`recon.t0rag.coef_rag`) because the replay logs hold sizes, not text. The live demo holds the text, so it counts the real tokens of the full and the sent request with the target model's tokenizer; the fidelity (exact or approximation) is shown and an approximation is never labelled exact. The same rules otherwise apply: uncached input, once per request, fees untouched, an unknown price is "not computed", never 0.
11. **Overhead:** the span `context.dedup` is part of the overhead total (100 ms budget). `scripts/measure_overhead.py` gains `--dup-chunks N` and `--dedup`. The demo's own number (2026-11-04, fake model, 2,000 synthetic requests of 8 chunks with half repeated, one laptop, indicative only, A-22): `context.dedup` p50 0.059 ms, p95 0.103 ms; the whole overhead p95 is 2.20 ms with dedup and 2.24 ms without; sent input tokens fall from 952,000 to 496,000. The sprint's replay figure (25 ms p95) is a different measurement and is not copied. Files: `reports/cost/overhead_demo_dedup_off.json`, `..._on.json`.

### Cache (Part 3)
12. **No new cache code.** `scope_rule = "demo_bot_level"`, the "new user" action and the optional `demo_seed` work with the new routing and context settings (tested with sticky, dedup and the bot-level scope); a cache hit still never anchors a session and the router's cache-hit behaviour is unchanged.
13. **The key uses the retrieved context as received, before dedup.** The cache lookup runs before the context build, from the measurements of the received request (ADR-0011, ADR-0034), so this follows from the existing key rules and needs no new decision. Consequences: two requests that differ only in duplicate chunks have different keys, so the second is a miss and never a wrong hit; the same original request hits whatever the dedup switch says. The dedup setting is not part of the key. A hit builds no context, so no dedup runs and the report shows none.
14. **Retrieval-result cache: nothing to wire.** The demo has no retrieval step and no retrieval fee: the retrieved context is pasted into the retrieval-context box (or comes from a stored bot) and travels on the request. `wiring/chat.py` and `wiring/demo.py` hold no retrieval call (a test guards the names). The cache toggles stay labelled DEMO and the serving scope stays `session`.

## Alternatives considered
- **A fifth decomposition term for dedup.** Rejected (point 10): breaks the fixed order and every reader of it; the sub-line gives the separate view.
- **Dedup as a field of `pass_through`.** Rejected: the task asks for a strategy selected by name, and a real bot's chat uses another layout (`dataset_positions`), so the strategy wraps a layout strategy.
- **Dedup in the cache key (key on the deduplicated context).** Rejected: it would let a request with duplicate chunks share an entry with one without them, which is a correctness claim about equal answers that no measurement supports. Keying on the received request is conservative.
- **A pointer or marker where a copy was removed.** Rejected: the sprint version had none, and it would add tokens and change what the model sees.
- **Swapping the demo catalogue and price file for the 2026-11-04 ones.** Rejected: the live files are hash-locked; the candidate set gives the same routing result without touching them.
- **Keeping the hosted and hybrid router modes in the toggles.** Rejected by the task: the demo spends nothing on routing.

## Consequences
- The demo routes over three models; most plain messages land on `gpt-4o-mini` through the safe tier (a visible, labelled property, not a quality claim).
- The default `ChatSession.router_mode` changed from `local` to `off`; callers that want a backend pass it explicitly (tests do).
- The `compression_saving` term now includes the dedup saving whenever the demo's dedup is on; the UI label says so.
- The dedup toggle is not in the cache key, so an answer cached with dedup off may be served with dedup on, and the other way round.
- Open for the owner: whether the demo should offer the result of the sprint's paid quality ablation once it exists; whether `deepseek-v4.1-flash` joins the demo candidates (it is not in the sprint set).
- Guarding tests: `tests/unit/domain/test_domain_context_dedup.py`, `test_domain_routing_candidates.py`, `tests/integration/test_demo_sprint_winners.py`, `tests/integration/test_demo_dedup.py`.
