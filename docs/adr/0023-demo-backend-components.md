# ADR-0023: Demo A backend: placeholder routing, detectors, demo cache settings, and experimental compression, promoted as labelled demo components

- Status: **decided for the demo** (Demo milestone, part A: the backend, 2026-10-19). Every component below is a **placeholder** until the Stage 8-plan experiments give evidence; none is a tuned or evidence-backed choice. The **serving defaults do not change** (`fixed_model` routing, `session` cache scope, the full key, `pass_through` context, no compression, providers' default thinking).
- Date: 2026-10-19
- Decision owner: the project owner (Demo A request of 2026-10-19; [brief](../project/live_testing_and_demo_brief.md) §6–§9, §12).
- Resolves: **A-64** (the `Turn` producer field). Uses Q-34 (DeepSeek thinking as configuration), Q-37/Q-38 (plans' thresholds stay provisional).
- Relates to: ADR-0007, ADR-0009 (repository_structure §6.2), ADR-0010, ADR-0011, ADR-0013, ADR-0016, ADR-0017, ADR-0018, ADR-0020, ADR-0021; [routing_plan.md](../experiments/routing_plan.md) R1, R8; [caching_plan.md](../experiments/caching_plan.md) C4; [context_plan.md](../experiments/context_plan.md) X3, X4.

## Context

The Demo milestone needs a working backend before the UI (Demo B): rule-based and sticky routing over the five test models, language and code features, a demo cache scope and seed, LLMLingua-2 as a labelled toggle, DeepSeek thinking on/off, and a terminal chat that shows all of it. repository_structure §6.2 normally promotes a strategy only with evidence against both baselines. No routing, cache-scope, or compression experiment has run yet (they need recorded or live answers and a judge). The demo needs the components in the package, behind the import rules, tested, and selectable by configuration.

## Decision

1. **Promotion under §6.2 steps 2–5, without step 1 (evidence), as labelled demo components.** Each is in the right package and obeys the import rules (domain: pure, contracts only), has offline tests, is selectable by one configuration entry, is in the module reference, and says *demo* / *placeholder* (or *EXPERIMENTAL*) in its docstring and configuration comments. They stay placeholders until the named experiment reports: `rule_based` (exp-route-002), `sticky` (exp-route-010), demo cache settings (caching plan C4), LLMLingua-2 (context plan X3).
2. **Features (FR-FEAT-01, -03).** `domain/features/detectors.py`: language by script and words (Persian, English, mixed, other, undetermined; code removed first; Arabic-script counts as Persian unless an Arabic-only letter and no Persian-only letter appear), code (fences, strong and weak signals), length buckets (configured character bounds), greetings and small talk (a configured Persian + English phrase list, whole message only, at most `max_chars`; never "short = trivial"). Feature set `fs-0.2.0-demo`. Each earlier user turn also gets these features plus the producer of its answer (`RequestFeatures.history_turns`).
3. **Routing.**
   - `rule_based`: ordered rules over features choose a tier; inside the tier, the eligible model with the lowest **effective** cost per answer: input plus an assumed visible output plus each model's **expected hidden reasoning tokens**, all billed at the output price (routing plan §3). The expected reasoning values are placeholders from one tiny live check each; a model that bills reasoning but has no value gets `default_reasoning_tokens` (never zero); a model whose thinking is disabled gets zero. The escalation chain is the cheapest model of each higher tier.
   - `sticky` with `mode = sticky_v1 | per_request`, exactly the brief's §7: greetings never anchor and go to the cheapest model (in an anchored session they stay on the anchor: amendment 1); cache-served turns never anchor; the first substantive message anchors; similar messages stay; a very different message (code appears or disappears, an attachment appears, the language switches, the length bucket moves by `length_bucket_jump`) re-routes and re-anchors; an escalation raises the anchor, never lowers it. `per_request` applies the rules to every message.
   - **Stateless (P-8):** the anchor is reconstructed on every request from the history in the request. Nothing is stored between requests.
   - `[pipeline.routing] policy` stays `fixed_model` in `defaults.toml`; `scripts/chat.py` selects `sticky`.
4. **A-64 resolved: `Turn.producer: Component[Name]`** (optional, tri-state), contract schema **0.4 → 0.5**: present = a catalogue model ID or `cache`; absent = a user turn (a user turn may not carry a present producer); unknown = not recorded (the default: logged history, old callers). The producer is **metadata, not content**: it is not part of the history fingerprint, so it never splits a cache key. The chat session fills it on every turn. Other 0.5 additions: `RequestFeatures.length_bucket`, `is_greeting`, `history_turns` (`TurnFeatures`); `RoutingDecision.anchor_model_id`; `ContextAction.COMPRESSED`; the `context_compressed` event (`ContextCompressed`, sizes only); span `context.compress` (overhead); `IneligibleReason.NOT_FIRST_TURN`.
5. **Caching for the demo (labelled DEMO settings; serving defaults unchanged).**
   - `[pipeline.cache] scope_rule = "demo_bot_level"`: `global` scope only when instructions are present, so entries are shared by every user of one bot through the instructions fingerprint (and the retrieved context, history, and target group) already in the key. It is ADR-0016's S-b shape **without** its traffic-source rule and its prerequisites (time-sensitivity detector, false-hit rates, privacy review); that is why it is a demo setting and never a serving option. Default `fixed` (the configured scope, `session`).
   - `[pipeline.cache.demo_seed] enabled = true`: a few first-turn sample questions with one clean logged answer, stored under a **message-only** key variant `demo_seed_msg_only` (its own key schema, global scope, no target group, `serving_allowed = false`). Looked up only when enabled, only after a main-cache miss, only for first-turn requests without attachments. Logged answers are served locally from the cache and **never sent to a provider**; `served_by: cache`, model `demo-seed`. Off by default.
6. **Context: LLMLingua-2 as an EXPERIMENTAL strategy** (`[pipeline.context.compression]`, off by default). Only history turns and retrieved items of at least `min_chars` are compressed; **instructions never by default** (an explicit `compress_instructions` opt-in exists for experiment arms only); the current message never. The compressor is a port (`TextCompressor`) called by `application` (P-1); the domain decides what is compressed and marks the composition record. Model: `microsoft/llmlingua-2-xlm-roberta-large-meetingbank` (MIT), revision `ebaba9b0…`, run with `llmlingua` 0.2.2 on CPU. Weights and the tiktoken file that `llmlingua` loads come only from `scripts/fetch_compressor_assets.py` (sha256-pinned, `data/compressors/`, git-ignored); the adapter verifies every file, loads with the Hugging Face libraries offline, and refuses remote code. Libraries in the optional extra `compress`, locked separately in `requirements-compress.lock` (the dev lock plus the extra); never in the runtime lock. Compression time is overhead (span `context.compress`); the tokens it removes reach the decomposition's compression term through the request actually sent. A labelled SYNTHETIC fake compressor shows the mechanics offline.
7. **Original LLMLingua (X4): not built.** LLMLingua-2 (a 560M-parameter encoder, one forward pass per chunk) already takes about 310 ms on this CPU for a 300-character text, three times the 100 ms p95 budget. Original LLMLingua scores tokens with a causal LM (default `NousResearch/Llama-2-7b-hf`, 7B parameters, about 13 GB in half precision, more in the float32 that `llmlingua` uses on CPU), iteratively; it can only be slower, and no small causal LM with verified Persian coverage was identified. It stays an optional arm of the context plan for a GPU or a later, smaller model.
8. **DeepSeek thinking per request configuration (Q-34).** `[model_options."deepseek-v4-flash"] thinking = "disabled"` is sent in each request's body; default unchanged (thinking on). The tokenizer table gains `mode_templates`: wiring uses the `thinking_disabled` template for a model whose options select that mode (DeepSeek: framing 5 for system + user, from the probe's 40 reported tokens; MiMo: ChatML with `<think></think>` priming, unverified). The chat toggles it by rebuilding its pipeline between turns.
9. **Terminal demo (`scripts/chat.py`, `wiring.chat`).** Commands for the routing mode, compression (real or fake), bot-level cache, seed, DeepSeek thinking, a new user of the same bot, and an offline escalation (`/degrade`). Each turn reports the routing decision and its reason, features, cache lookups, served by, model, tokens, cost, premium estimate, the full decomposition, compression, overhead, budget, and settings, content-free. A toggle rebuilds the pipeline but keeps the cache store and the fingerprint key, so cached entries stay reachable.

## Alternatives considered

- **Keep the components in `experiments/` and load them for the demo with `[experiment.strategy]`.** That mechanism is for experiment runs (one candidate, run records); the demo needs several components together, long-lived chat sessions, and a teammate quickstart. Rejected for the demo; experiments still load candidates the usual way.
- **A request-level summary of producers instead of a `Turn` field (A-64's other option).** Loses per-turn information that sticky re-anchoring needs. Rejected.
- **Store session state (the anchor) in the pipeline.** Breaks P-8 (stateless) and replay. Rejected.
- **Rank by nominal price.** Picks gpt-5-nano for cheap tiers, which bills hundreds of hidden reasoning tokens on tiny answers. Rejected (routing plan §3).
- **A new `instruction_group` scope value for the demo.** ADR-0007 rejected it; S-b needs none. Rejected.
- **Re-implement LLMLingua-2 directly on `transformers`.** Fewer dependencies, but not the reference implementation the plan names. Rejected for now; revisit if `llmlingua` (last released 2024-04) stops working with current `transformers`.
- **The smaller multilingual LLMLingua-2 model (`bert-base-multilingual-cased`, 710 MB).** Faster, but the brief names XLM-RoBERTa-large. Kept as a candidate for the context plan's latency arm.

## Consequences

- Contract schema 0.5 (contracts_reference.md regenerated). Data written under 0.4 is not guaranteed readable (contracts.md §2.7); no persisted data depends on it.
- The demo's routing numbers are placeholders: they show the mechanism, not a saving that anyone may cite. The effective-cost model sends most short messages to `mimo-v2.5` (its output price is the lowest in tier 0). Xiaomi retires that ID on 2026-10-21 (A-60, TODO-13): live demo calls to it may then fail with `invalid_request`, which is not retried or failed over.
- LLMLingua-2 overhead (§7) is far above the 100 ms budget on CPU, and it removes Persian ZWNJ in its output; both are recorded (reports/cost, A-67) and are reasons it stays experimental.
- `requirements-compress.lock` is resolved on macOS arm64; torch's Linux dependencies differ, so the Docker images do not include the extra (TODO-14).
- New register entries: A-64 decided; A-65…A-70; Q-40…Q-42; TODO-14.
- Demo B (Streamlit UI, bot-setup presets, cost panel) reuses `ChatSession` and `TurnReport`; it adds no logic.

## Amendment 1 (2026-10-19, owner decisions Q-40, Q-41, Q-42)

- **Q-41: greetings in an anchored session stay on the anchor.** `sticky_v1` sends a greeting or small talk to the anchor model when the session is anchored and the anchor is eligible (reason `sticky.greeting.stay`), to keep the provider's prefix cache warm; a greeting costs almost nothing on any model. Only an unanchored session (or an ineligible anchor) sends it to the cheapest model (`sticky.greeting`). A greeting still never anchors. This departs from the brief's §7 wording on purpose (owner decision); A-70 updated.
- **Q-40:** original LLMLingua stays a **deferred** arm of the context plan (X4) until a GPU or a small Persian-capable causal LM is available (point 7 unchanged).
- **Q-42:** on 2026-10-21 the owner checks the Metis pricing page: if Xiaomi's new MiMo ID is listed, switch to it (a new catalogue row and a dated price file, configuration only, TODO-13); otherwise set `mimo-v2.5` `enabled = false`, and routing falls back to the next-cheapest eligible model. Procedure in the quickstart's troubleshooting.
- **Live check of the whole flow** approved (output cap 512): [metis_demo_live_check.md](../references/metis_demo_live_check.md).

## Amendment 2 (2026-10-19, owner request: coding intent)

- **Gap:** "write a python function to add two numbers" has no code, so code presence is correctly `no`, and sticky routing kept it on the anchor (a tier-0 model).
- **A separate placeholder feature, coding intent** (`detect_coding_intent`, `[pipeline.features.coding_intent]`, A-71): the message asks for code or programming help **and has no code**. True when a word template matches ("write ... function", «تابع ... بنویس»; `...` = up to `max_gap` words), or when a configured keyword (python, function, error, کد, تابع, خطا, …) and a request cue (write, how, can you, بنویس, چطور, …) both appear. Prose that mentions programming without asking ("I studied python") is no. `exclude_phrases` («کد تخفیف», "discount code", …) are removed before matching keywords; keywords are whole words (a prefix «کد» would match «کدام»). Feature set `fs-0.3.0-demo`; contract schema **0.5 → 0.6** (`RequestFeatures.has_coding_intent`, `TurnFeatures.has_coding_intent`).
- **Used in** (a) `rule_based`: rule `coding_intent` → tier 1, like code presence (`RuleCondition.has_coding_intent`); (b) `sticky_v1`'s "very different" check: reason `coding_intent_appeared`, only when it **appears** (a follow-up without it stays) and only against an anchor without code. Shown in `scripts/chat.py`'s features line.
- **Known limits:** keywords, not meaning. A shop customer's "how do I fix this payment error" («چطور خطای پرداخت رو رفع کنم») is a false positive (tested and stated); «برنامه» also means "plan". Cost below 0.5 ms on a 2,000-character message.
