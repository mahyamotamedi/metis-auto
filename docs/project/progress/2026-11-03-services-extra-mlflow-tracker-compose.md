### Decisions and caveats
- **File store:** MLflow 3.17 refuses the file store unless `MLFLOW_ALLOW_FILE_STORE=true`; the adapter sets it (`setdefault`) for `file:` URIs. `mlflow-skinny` has no SQL backend.
- **`mlflow-skinny` cannot serve the UI** (needs flask). Logging needs only skinny. **The UI itself was not opened:** installing the full `mlflow` in a throwaway venv stalled on the network (twice, over 25 minutes), so the "UI shows every run" check is open. What was verified instead: the runs are read back from `runs/mlruns` through the MLflow client (172 runs, none missing a pin).
- **Lock method:** `pip-compile --generate-hashes` hung on `cryptography` 50.x (sdist-only, needs Rust) and then failed on connection resets while downloading wheels to hash them; the lock was compiled with `--only-binary :all:` and hashes taken from PyPI's JSON digests, as `constraints-min-age.txt` describes for earlier locks. Some `# via` comments for packages that gained new dependents (e.g. `typing-extensions`) are not updated.
- **Not verified:** the Dockerfile `demo` target (three locks in one `pip install --require-hashes`), the `redis:7-alpine` and `ghcr.io/mlflow/mlflow:v3.1.1` image tags (the server is older than the 3.17 client), and the Compose health checks, because no image was built or pulled.
- **Lever files:** the four `route.small_classifier.strict_unknown_blocked.*` files differ from HEAD (re-run in the Stage 1-6 candidate change, see that entry); not touched here.
